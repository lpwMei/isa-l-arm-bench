## 源码与集成

- Redis 基线：官方 7.0.15，提交 f35f36a265403c07b119830aa4bb3b7d71653ec9。
- 优化来源：https://gitee.com/chenxuqiang2022/crc16_bench ，提交 f8e9dbea5bd065823f0f77532136851e1d25dd0c。
- 导入推荐的 crc16_xmodem_pmull.S 四路折叠实现，算法代码保持上游内容，补充其注明的 Arm BSD 来源声明和 GNU-stack 标记。
- Linux AArch64 小端构建默认启用，启动时读取 HWCAP_PMULL；长度 >= 64 且支持 PMULL 时进入汇编，其余保持 Redis 原表算法。没有全局增加 crypto 编译选项。
- 接口仍为 uint16_t crc16(const char *, int)，初始值 0，多项式 0x1021；哈希标签及槽位映射逻辑不变。负长度仍返回 0。
- make CRC16_PMULL=no 可关闭；其他平台保留原版路径。切换编译选项后由 Redis 原有构建机制重建。
- 不导入实验 8-way 或短缓冲汇编路径。本需求 64B key 使用四路实现；短 hash tag 继续走原算法，收益不能直接外推。

## 测试方法

单 Redis 实例开启 cluster-enabled，独占全部 0–16383 槽，cluster_known_nodes=1、cluster_state=ok。正式重复测量固定 127.0.0.1:36380（总线 46380）。初测使用 16380，一次后续启动遇到瞬态端口占用，失败日志保留在 repeated-attempt1；该次未产生吞吐样本，未纳入统计。

每版服务端相同绑核、端口、配置及预热；轮次顺序 AB / BA 交替。客户端始终使用同一个基线 CRC16 的二进制，避免客户端优化混入服务端收益。

并发连接 200，pipeline 16；key 严格为 64B，无 hash tag；value 64B。随机 keyspace 10,000，SET 后进行 GET；验证数据库中实际 key/value 长度及 GET 命中。默认单线程客户端，不设置 --cluster：Redis 7.0.15 的该选项拒绝单节点集群，且会用短 hash tag；直接连接持有全部槽的单实例仍真实执行服务端集群 CRC16 路径。

原生 -d 64 设置 value 长度，不能满足 key 64B。故使用原生自定义命令模式分别执行 SET / GET，完整参数记录在每项 .command.json：

```bash
KEY=$(printf 'k%.0s' {1..52})__rand_int__  # 52 + 12 = 64 bytes
VALUE=$(printf 'v%.0s' {1..64})
taskset -c 322,324,326,328 baseline/src/redis-benchmark \
  -h 127.0.0.1 -p 36380 -c 200 -P 16 -n 10000000 -r 10000 --csv SET "$KEY" "$VALUE"
taskset -c 322,324,326,328 baseline/src/redis-benchmark \
  -h 127.0.0.1 -p 36380 -c 200 -P 16 -n 10000000 -r 10000 --csv GET "$KEY"
```

每轮每版每项 1,000 万请求，共 24 个计时样本、2.4 亿计时请求；每项另有 20 万预热请求，不计入吞吐样本。统计量为两组吞吐中位数的比值减一。server INFO 计数交叉核验实际命令数，并断言计时阶段无新增错误回复。

## 功能与回归

- PMULL 路径、屏蔽 HWCAP_PMULL 的真实调度回退、完全不编译 PMULL 的标量路径，各 362,327 个差分用例通过，共 1,086,981 个。
- 验证 XMODEM 标准向量 123456789 → 0x31c3，全部 65,536 个双字节组合，0–4096 全长度 × 64 种偏移，随机及 1MiB 输入，固定二进制模式、零/负长度；缓冲区前后 PROT_NONE 页面检查越界读。
- 每次实例启动验证 1,039 个 key 的 CLUSTER KEYSLOT，与 Python binascii.crc_hqx 参考结果一致；覆盖空 key、NUL/高位字节、长 key、空/嵌套/不完整 hash tag。
- 二进制 key/value 的 pipeline SET/GET、GET miss、同槽多 key 操作、CROSSSLOT 错误语义通过。计时阶段没有新增错误回复，Redis 正常退出。
- 可执行栈检查 GNU_STACK 为 RW；关键反汇编、二进制 SHA256、编译日志已保存。
- 完整 CRC16_PMULL=no 构建：PASS（符号表中未链接 PMULL 实现）。
- Redis 原生 unit/cluster、unit/type/string、unit/keyspace 回归：全部通过；详细输出见 redis-regression.log。原生 cluster 回归按 Redis 测试框架创建多个临时节点，仅用于回归检查；上述性能测试始终是单节点集群。

CRC16 微基准（同一 CPU，独立函数调用）：64B 原版 139.127ns，优化版 8.370ns，约 16.62 倍。该数字仅描述 CRC16 函数，与主表 Redis 端到端吞吐分开统计。

## 100 亿请求计数修复

Redis 7.0.15 原生客户端的 requests、issued、finished、previous 为 int，且 -n 使用 atoi；10000000000 会溢出。独立 client-only 补丁将请求计数及局部副本改为 long long，使用带范围校验的 strtoll，修改完成数输出格式；服务端优化补丁不包含此改动。

实际解析 -n 10000000000、issued 越过 INT32_MAX、finished 越过 UINT32_MAX、previous 接近 100 亿的原子计数测试均通过，非法值 0、负数、超界数和尾随非数字输入拒绝。两组正式测量共用修复后的同一个客户端。短样本的初测使用未修改计数的原生客户端，仅作为 pilot 保留，不并入正式 6 轮统计。

## 后续复核：理论收益、采样与绑核


复核日期：2026-10-26。不能根据端到端吞吐的差值，直接断言全部收益来自 CRC16。原有 13.47% / 15.07% 是该环境的实测中位数，因果归因需要同工况热点与对照证据。

## 理论检查

采用固定工作量、其他开销不变的 Amdahl 模型：

`整体加速比 S = 1 / ((1-p) + p/k)`

其中 p 是优化前受影响部分占瓶颈服务时间的比例，k 是该部分加速比。模型参考 [Hill 与 Marty 的 Amdahl's Law in the Multicore Era](https://www.cs.cmu.edu/~18742/papers/Hill2008.pdf)。对流水线服务，必须使用瓶颈资源的服务需求口径，不能将用户态 perf 百分比直接当成整个客户端请求的墙钟时间比例。

本次 64B CRC16 微基准为 139.127ns → 8.370ns，k≈16.62。反推端到端结果需要的 p：

| 项目 | 测得吞吐提升 | 模型要求的原始占比 |
|---|---:|---:|
| SET | 13.47% | 12.63% |
| GET | 15.07% | 13.94% |

如果同工况、相同分母下 CRC16 仅占 2%，k=16.62 时理论收益约 1.92%；即使消除全部 CRC16 开销，理论收益也仅 2.04%。占 5% 时相应为 4.93% 和 5.26%。这种情况下 13%–15% 不能全归因于 CRC16，必须继续检查实验条件或其他变化。

## 新增基线采样

在原版 Redis 的 SET 长测期间，以 liupengwei 采集 `cycles:u`，499Hz、10 秒，4,991 个样本，无丢样。CRC16 占采样用户态 cycles 的 **19.21%**，933 个采样点命中该函数。

这说明本次完整 64B key、无短 hash tag、pipeline 16、小 value 工作负载中，CRC16 在用户态不是只有几个百分点。该比例只针对当前基线 SET，分母排除了内核时间、等待和其他进程，不能直接等同于上表 p；尚未采集优化版及 GET 同期热点，因而不能将整个吞吐差值完全归因于 CRC16。

容器中的 `/work/...` 路径在宿主机不可直接解析，perf 初始输出显示函数内地址。为避免错误归因，用同一个非 PIE redis-server 的 `nm -S` 地址区间解析绝对采样 IP；CRC16 的实际区间为 `[0x4b8910, 0x4b8958)`。按采样 period 加权汇总，原始采样、采样 IP、解析脚本及汇总 JSON 一并保留。

证据：`results/profile-baseline-set.data`、`profile-baseline-set-samples.txt`、`profile-baseline-set-summary.json`；解析脚本为 `analyze_profile.py`。

## 实际绑核

以下是 Linux 的逻辑 CPU / lscpu Core ID，Socket 1 表示第二颗处理器；本机只暴露 NUMA node 0。

| 用途 | 逻辑 CPU | Socket | 物理 Core ID | SMT 同胞 |
|---|---:|---:|---:|---:|
| Redis | 320 | 1 | 160 | 321 |
| 客户端允许集合 | 322 | 1 | 161 | 323 |
| 客户端允许集合 | 324 | 1 | 162 | 325 |
| 客户端允许集合 | 326 | 1 | 163 | 327 |
| 客户端允许集合 | 328 | 1 | 164 | 329 |

Redis 使用 `taskset -c 320` 启动，`io-threads 1`；实际检查主线程和各后台线程的 affinity 均为 320。基线和优化版使用相同配置。客户端用 `taskset -c 322,324,326,328`，与 Redis 不共享物理核。

主表客户端是一个线程，允许在这四个逻辑 CPU 间迁移；不是每线程固定到单独的一个核。四线程补测也共用该集合，未逐线程设置不同 affinity。容器 cpuset 额外包含 330、332、334，供构建和验证使用，不代表 Redis 同时使用八个核。

只设置了测试进程的 CPU affinity，未通过 cpuset 独占分区、isolcpus 或 IRQ affinity 排除其他任务及中断；SMT 同胞未由本测试使用，但没有禁止其他负载使用。不能称为系统级独占绑核，现有结果仍需保留共享机器环境的不确定性。

下一步归因应在相同 key、value、pipeline、客户端及同一物理核上，采集原版/优化版 SET/GET 的同期 cycles、指令和 CPU 服务时间，并固定客户端线程、检查同胞核及 IRQ 干扰；长测完成本身不能替代这些因果证据。

## 手测脚本与简化命令的区别

脚本长，是因为包含单节点集群启动、全槽分配、端口检查、绑核、预热、结果记录和实例停止。实际计时调用仍然是 redis-benchmark。

但脚本负载不与 `redis-benchmark -c 200 -t set,get -n 10000 -P 16` 严格等价：脚本还使用 `-r 10000`，完整64B key、64B value、各20万请求预热；此前报告每项每轮计时1000万请求。该短命令默认不随机化key，value默认3B，原生默认key也不是64B。

原生7.0.15的 `-t` 用逗号分隔，应写 `set,get`，`set.get` 不会选中 SET 或 GET。`-d 64` 是value长度，不是key长度。

下面两条命令满足：200连接，SET与GET各1万请求，pipeline16，固定64B key，value采用原生默认长度3B；不额外预热、不使用随机key空间。先启动手测 Redis，再在手测容器内执行：

```bash
KEY=$(printf 'k%.0s' {1..64})
taskset -c 342 /manual/bin/redis-benchmark -p 36381 -c 200 -n 10000 -P 16 SET "$KEY" xxx
taskset -c 342 /manual/bin/redis-benchmark -p 36381 -c 200 -n 10000 -P 16 GET "$KEY"
```

需64B value时，显式构造VALUE并替换xxx；这与默认3B value属于不同负载。1万请求适合检查流程，百万QPS时仅约10ms，不能据此获得稳定的热点占比或可靠的小幅吞吐差异。

`processInputBuffer → processCommand → getNodeByQuery → keyHashSlot → crc16`

容器的 `/work/...` 路径在宿主不存在，故在 `validation/perf-symfs` 镜像相同路径，放置正在运行的精确Redis二进制及容器libc。使用 `--symfs` 正常解析符号；新版结果无需依靠手工地址推断。部分libc启动栈帧仍显示unknown，Redis/CRC16路径已解析。

```bash
SYMFS="$PWD/validation/perf-symfs"
perf report -i results/profile-baseline-set-dwarf.data --symfs "$SYMFS" \
  --stdio --no-children --sort dso,symbol

perf script -i results/profile-baseline-set-dwarf.data --symfs "$SYMFS" \
  -F comm,pid,tid,time,period,event,ip,sym,dso \
  > results/profile-baseline-set-dwarf.script

perl artifacts/FlameGraph/stackcollapse-perf.pl \
  results/profile-baseline-set-dwarf.script > results/profile-baseline-set-dwarf.folded

perl artifacts/FlameGraph/flamegraph.pl \
  --title 'Redis 7.0.15 baseline SET - user cycles' \
  --subtitle '64B key, 64B value, c200 P16, 30s @199Hz; cycles:u only' \
  --countname cycles --width 1500 \
  results/profile-baseline-set-dwarf.folded > results/profile-baseline-set-flamegraph.svg
```

脚本显式导出period字段，因此火焰图宽度以cycles加权，不是简单数样本。folded总权重为59,575,835,441，CRC16为11,163,552,116，比例18.7384%，与perf report吻合。

工具为Brendan Gregg官方FlameGraph，提交41fee1f99f9276008b7cd112fca19dc3ea84ac32。源码：https://github.com/brendangregg/FlameGraph 。

## 查看方式与文件

- `results/profile-baseline-set-flamegraph.svg`：交互SVG，用浏览器打开；点函数块缩放，Search输入 `crc16` 高亮占比。
- `results/profile-baseline-set-flamegraph.png`：静态预览。
- `results/profile-baseline-set-dwarf-report.txt`：函数热点与调用链文本。
- `results/profile-baseline-set-dwarf.folded`：按cycles加权的折叠调用栈。
- 服务器上的 `results/profile-baseline-set-dwarf.data` 和 `.script`：原始采样和解码调用栈，保留在上述工作目录。
- `flamegraph-raw.tar.gz`：这两个原始文件的本地交付归档，解压后可以重新生成并核验火焰图。

采样阶段会引入一定观测开销；这30秒用于热点归因，不作为新的独立吞吐样本。图中分母只包含被采样Redis进程的用户态cycles，不含内核和等待时间。
